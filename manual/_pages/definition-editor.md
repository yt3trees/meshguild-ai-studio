エージェント・チーム・グラフの定義は YAML ファイルが真実の源ですが、最初の 1 本を白紙から書くのは負担が大きい作業です。Web 画面には、エージェントの基本設定やチーム、グラフを雛形から始め、参照先を一覧から選び、保存前に日本語で検証結果を受け取るための導線が用意されています。このページではその使い方と、Claude Code のようなコーディングエージェントへ定義作成を任せる方法を紹介します。

YAML を直接書く方法を知りたい場合は、[エージェントを作る]({{ '/pages/agents/' | relative_url }})、[チームを作る]({{ '/pages/teams/' | relative_url }})、[グラフを作る]({{ '/pages/graphs/' | relative_url }})を参照してください。画面で作った定義も、書き出されるのは同じ形式の YAML です。

## 何が楽になるか

YAML を手で書くときに詰まる箇所は、だいたい次の 3 つに分かれます。画面はこの 3 つをそれぞれ別の方法で解消します。

| 詰まる箇所 | 画面での解決 |
| --- | --- |
| 何から書き始めればよいか分からない | 用途別の雛形を選び、そこから直す |
| どのキーがどの場面で有効か分からない | ノード種別に応じて、意味を持つ項目だけを表示する |
| 参照した名前が実在するか分からない | エージェント名やノード ID をすべて選択式にする |

## 新しい定義を作る

左のナビゲーションの New definition(`/definitions/new`)から始めます。作りたい種類(エージェント / チーム / グラフ)と、始め方(テンプレートから / 既存を複製 / 文章から生成)を選びます。

### テンプレートから

用途別の雛形が用意されています。それぞれに「何を作る雛形か」と「どういうときに選ぶか」が書かれているので、迷ったら上から読んでください。

| 種類 | 雛形 | 用途 |
| --- | --- | --- |
| チーム | レビュー体制 | 実装役の成果を検証役が確かめる 3 名構成 |
| チーム | 調査と執筆 | 調査役が集めた材料を執筆役がまとめる 3 名構成 |
| チーム | 最小構成 | 統括と担当 1 名。チーム定義として成立する最小の形 |
| グラフ | 直列 3 ステップ | 計画、実行、まとめを順に流すだけの一本道 |
| グラフ | 承認つき | 下書きを作り、人の承認を挟んでから確定処理へ進む |
| グラフ | 品質ループ | 評価者の点数が基準を超えるまで書き直しを繰り返す |
| グラフ | 並列と合流 | 2 つの作業を同時に走らせ、両方揃ってからまとめる |

雛形を選ぶと、埋めるべき箇所(統括、実装役など)が一覧で出ます。それぞれ既存のエージェントから選びます。選ぶたびに右側の「これはこう動きます」が更新されるので、作る前に内容を確認できます。

### 既存を複製

すでにある定義を写して名前を変えます。動いている定義をひな型にするのが、実は一番手早く覚えられる方法です。

### 文章から生成

日本語の要望から草案を作ります。「経費申請の内容をレビューするチームがほしい。実装役が下書きを作って、検証役が規程との齟齬を指摘する形にしたい」のように、誰が何を担当するかと進め方を書くと精度が上がります。

生成された草案は、そのまま保存されるわけではありません。必ずスキーマ検証と参照検証を通したうえで編集画面に読み込まれるので、内容を確認してから保存してください。この機能を使うには [Models 画面]({{ '/pages/configuration/' | relative_url }})で LLM モデルを 1 つ以上設定しておく必要があります。

### 名前と保存先

`name` はフォルダー名になるため、英小文字、数字、ハイフン、アンダースコアだけが使えます。既存の定義と同じ名前は付けられません。

保存先は画面に表示されます。定義ソースを複数設定している場合は、最後のソース(後勝ちで最優先されるソース)に書き出されます。設定については[設定]({{ '/pages/configuration/' | relative_url }})の `Agents:DefinitionSources` を参照してください。

## チームを編集する

Teams &amp; Agents でチームを選び、右上の「編集」から開きます(`/teams-agents/<name>/edit`)。

- 統括とメンバーは、登録済みのエージェントから選ぶドロップダウンになっています。選択肢に出るのは YAML に書き込まれる `name` そのもので、括弧の後ろに表示名と説明が補足として出ます
- 直接会話の許可(`channels.allow`)の相手は、そのチームにいるエージェントだけに絞られます。チームにいない相手を選んでしまう事故が起きません
- メンバーを削除すると、そのメンバーを指していた直接会話の経路も一緒に消えます
- 各項目のラベルの下に出る説明文は、`schemas/team.schema.json` の `description` をそのまま表示しています。画面とスキーマで説明がずれることはありません

## グラフを編集する

Graph Studio でグラフを選ぶと、キャンバスと右側のインスペクタが開きます(`/graphs/<name>`)。

![Graph Studio の画面。検証ボタン、グラフキャンバス、右側のインスペクタに番号付きの注釈があります。]({{ '/assets/images/graph-studio.png' | relative_url }})

1. 「検証」や保存を行うツールバー
2. ノードとエッジを配置するキャンバス
3. 選択したノードを編集するインスペクタ

### ノードの編集

キャンバス上のノードをクリックすると、そのノードの種別で意味を持つ項目だけが出ます。`kind: agent` ならエージェントと入力、`kind: loop` ならループ本体と停止条件、`kind: join` なら合流方針、といった具合です。使わない項目は最初から出ないので、どのキーがどこで効くのかを覚えていなくても書けます。

`kind` を変えると、新しい種別では意味を持たなくなった項目は自動的に消えます。読み手を惑わせる値が YAML に残りません。

エッジの `from` / `to`、`loop` の本体サブグラフ、`join` の迂回先といったノード参照も、すべてそのグラフ内のノードから選ぶ形式です。ノード ID を変更すると、そのノードを指していたエッジと座標も一緒に追随します。

### エッジとグラフ全体

インスペクタ上部のタブで、エッジ一覧とグラフ全体の設定(名前、既定チーム、既定予算)に切り替えられます。YAML タブでは、保存したときに書き出される内容をそのまま確認できます。

## 動きの説明を読む

編集画面の下(チームの場合は右)には、「この定義はこう動きます」という日本語の説明が常に出ています。

```text
start   エージェント repo-agent に「${mission.goal}」を渡して任せる。その後は route へ進む。
route   条件を見て経路を分ける。その後は parallel へ進む、${mission.id} == 'never' が真なら fallback へ進む。
verify  サブグラフ improve-body を繰り返す。2 回まで、スコアが 0.9 以上になったら停止する。
```

書いた本人の検算になるだけでなく、レビューする側が YAML を読まずに意図を確認するためにも使えます。

## 検証結果の読み方

「検証」を押すと、保存前に問題を確認できます。エラーコードや英文ではなく、何が起きているかと、どう直せばよいかが日本語で出ます。

```text
ループノード improve に停止条件 (stop) がありません。
  maxIterations (回数)、costLimitUsd (コスト)、timeLimitSeconds (時間)、scoreThreshold (スコア) のうち
  1 つ以上を指定してください。どれも無いと止まらなくなるため必須です。

分岐ノード route から出るエッジすべてに condition が付いています。
  どの条件にも当てはまらなかったときの行き先が無く、実行がそこで止まります。
  condition を書かないエッジを 1 本足して、既定の経路にしてください。
```

問題のあるノード ID はボタンとして表示され、押すとキャンバス上のそのノードが選択されます。

保存は検証を通ったときだけ行われます。問題が残っている定義がファイルに書き出されることはありません。

## 保存するときの注意

- 保存した内容が実行に反映されるのは、アプリを再起動したあとです。定義は起動時に読み込まれるためで、画面上の一覧には保存直後から反映されます
- 画面から保存すると、元の YAML に書かれていたコメントは失われます。コメントで説明を残している定義は、画面で保存せず直接編集してください
- `subgraphs`(ループ本体などの内部グラフ)の中身は画面から編集できません。件数の表示のみで、編集は `graph.yaml` を直接開いてください

## コーディングエージェントに作らせる

画面のフォームや YAML の直接編集とは別に、Claude Code のようなコーディングエージェントへ定義作成そのものを任せる方法もあります。そのための Agent Skill が同梱されています。

| スキル | 作るもの |
| --- | --- |
| `create-agent` | エージェント定義(`agent.yaml` と `instructions.md`)。役割、指示、harness の権限を決める |
| `create-team` | チーム定義(`team.yaml`)。統括とメンバー、会話経路、ガードレールを決める |
| `create-graph` | グラフ定義(`graph.yaml`)。ノード、エッジ、分岐、並列、合流、ループ、承認、`code` ノードのスクリプト |
| `graph-design` | いきなり `graph.yaml` を書かず、業務の目的から工程を対話的に設計し、Mermaid 図付きの設計書へ落とす |

### 置き場所

- ソースから使う場合：リポジトリ直下の `.agents/skills/`
- 配布物を使う場合：`dist\definitions\.agents\skills\`

配布物の `definitions` フォルダーには、実行時に読み込まれる定義(`agents`、`teams`、`graphs`、`skills`)と並んで、この作成用スキルが `.agents\skills\` として入っています。エージェントが実行時に参照する共有スキル(`definitions\skills\`)とは別物で、`.agents` 側は定義を書く人間とコーディングエージェントのためのものです。

### 使い方

スキルを含むフォルダーを作業ディレクトリにしてコーディングエージェントを起動し、作りたいものを日本語で依頼します。

```text
経費申請の内容をレビューするチームを作ってください。
実装役が下書きを作り、検証役が規程との齟齬を指摘する形にしたいです。
```

スキルは `schemas/*.schema.json` を形式の正本として読み、ローダーが弾く条件(フォルダー名と `name` の不一致、未知のキー、存在しないエージェント名の参照など)まで含めて書きます。そのため、画面のテンプレートより込み入った定義や、コメントを残した YAML を作りたい場合に向いています。

生成された定義も、そのまま動くとは限りません。次の点は人が確認してください。

- グラフは画面の「検証」または `POST /graphs/<name>/validate` を通す
- チームは読み込み時に検証されるため、Host を起動して `GET /teams/<name>` が返ることを確認する
- どの定義も、実行へ反映するには再ビルドと再起動(配布版はトレイメニューの「更新」)が必要

## VS Code での補完も併用する

画面を使わず YAML を直接書く場合も、`.vscode/settings.json` でスキーマが紐付けてあるため、VS Code 上でキー名の補完と検証が効きます。画面で骨格を作り、細かい調整はエディタで、という進め方もできます。
