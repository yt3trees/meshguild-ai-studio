# グラフ設計スキル

## 目的

WorkAgents のグラフを、YAML の項目からではなく、実行する仕事の責務と受け渡しから設計する。
設計の結果は `graph.yaml` の草稿だけでなく、第三者が読んで実行経路・停止条件・失敗時の扱いを理解できる設計書にする。

グラフ設計では、すべてのノードをエージェントにしない。決まった処理は `code`、判断が必要な仕事は `agent` または `team`、取り返しのつかない操作の直前は `approval` として分離する。これにより、実行結果の再現性、費用の見積もり、監査可能性を保つ。

## 参照資料

設計書を作るときは、最初に次のテンプレートを読む。

`references/graph-design-template.md`

WorkAgents の実装に落とす前に、リポジトリ内の次の一次情報も確認する。

- `schemas/graph.schema.json`: 使用できるフィールドと型
- `manual/_pages/graphs.md`: ノード種別、式、Graph Studio の挙動
- `specs/001-multi-agent-orchestration/contracts/graph-yaml.md`: 実行意味論と検証規則
- `.specify/memory/constitution.md`: 秘密情報、承認、Local-First、ファイル定義の原則

一次情報とテンプレートの記述が食い違う場合は、スキーマと契約を優先し、設計書の前提に差分を明記する。

## 対話の進め方

### 1. 目的を固定する

ユーザーの説明から次を埋める。情報が不足している場合は最大 5 個の質問をまとめて聞く。既に文脈から判断できる項目は質問で止めず、仮定として明記して進める。

- 何の業務を自動化するか
- 開始条件とミッション入力は何か
- 成功を何で判定するか
- 成果物と最終出力は何か
- 対象外にする範囲は何か
- 外部書き込み、削除、公開、課金などの危険な操作はあるか
- 失敗、タイムアウト、差し戻し、再実行をどう扱うか

「とりあえず graph.yaml を書く」と言われても、入力、出力、完了条件が不明なまま YAML を完成品として出さない。先に設計書の最小版を作り、未決事項を残す。

### 2. 業務を責務へ分解する

ノードは「1 つの責務」と「1 つの完了条件」を持つ大きさにする。次の表で分類する。

| 分類 | WorkAgents の種別 | 使う場面 |
|---|---|---|
| 決定的処理 | `code` | 取得、整形、検査、集計、パッケージ化など、同じ入力なら同じ結果にすべき処理 |
| エージェント判断 | `agent` / `team` | 読解、比較、提案、レビュー、自然言語による判断 |
| 人間の判断 | `approval` | 外部公開、削除、リリース、支払い、権限変更など、結果が集中する操作の直前 |
| 経路制御 | `branch` / `parallel` / `join` / `loop` / `subgraph` | 判断そのものではなく、仕事の流れを制御する処理 |

各ノードについて、入力、出力、完了条件、失敗条件、担当する定義、再実行単位を設計書に書く。エージェントに「うまくやる」だけを返させず、後続ノードが判定できる状態や成果物参照を返させる。

### 3. トポロジーを描く

最初に Mermaid の全体図を作り、次にノード表とエッジ表を埋める。図は説明用、`graph.yaml` は実行の正本として扱う。

- 分岐はエッジの `condition` に書き、条件なしの既定経路を 1 本用意する
- 互いに待つ必要がない処理は `parallel` から分ける
- 並列結果の待ち方を `joinPolicy: all` または `any` で決める
- 一部失敗時の `onPartialFailure` と迂回先を決める
- 戻りのエッジには `loopBack: true` を付け、`loop.stop` に上限を置く
- サブグラフは入出力契約を決め、相互再帰を作らない

ループは「いつか終わる」と書かない。最大回数、コスト、時間、評価スコアの少なくとも 1 つを具体化し、上限に達したときの停止または人間へのエスカレーションを設計する。

### 4. データ契約を決める

ノード間で渡す値を、設計書の入出力表とデータフロー表で定義する。

- `${mission.goal}` と `${mission.id}` の用途を明記する
- `${nodes.<id>.output}` または出力キーの producer と consumer を明記する
- 出力の型、必須キー、成功値、失敗値を決める
- 大きな本文を状態に持ち回らず、成果物 ID、パス、URI、要約など薄い参照を渡す
- API キー、アクセストークン、秘密鍵、秘密値を設計書、YAML、プロンプト、成果物、ログへ書かない

参照先の agent、team、graph、node ID は推測で作らない。実在する定義と一致することを確認する。

### 5. 失敗と安全性を設計する

正常経路だけで設計を終えない。少なくとも次を失敗表へ追加する。

- 入力不正、参照先不在、グラフ検証エラー
- agent、team、code の失敗とタイムアウト
- `join` の一部失敗
- approval の却下、期限切れ、承認待ち
- loop のスコア未達、最大回数、コスト上限、時間上限
- 成果物の保存失敗、外部サービスの一時障害

危険な処理を `code` や agent に直接任せるだけで安全と判断しない。承認ノード、実行側の再検証、作業ディレクトリ拘束、予算上限、監査情報を組み合わせる。

### 6. YAML へ写像する

設計書が固まった後に `graph.yaml` の草稿を作る。テンプレートの YAML 対応表を使い、次を機械的に照合する。

- `version: 1`、`name`、フォルダー名が一致している
- 設計書の全ノードが YAML にあり、YAML の全ノードが設計書にある
- node ID と edge ID が一意である
- `from` と `to` が実在する node ID を指す
- `agent`、`team`、`graph` の参照先が実在する
- `code` のスクリプトは `scripts/*.csx` に置く
- branch に既定経路がある
- loop に停止条件があり、loopBack と矛盾しない
- `${...}` の参照先と条件式が検証規則に適合する

`nodes[].next` は表示用の非推奨項目であり、設計の根拠や実行順序に使わない。実行順序は `edges` だけで表す。

### 7. 検証と読み手テストを行う

Graph Studio または `POST /graphs/<name>/validate` で保存前検証を行う。さらに、`ScriptedAgentInvoker` を使って LLM や API キーなしで次を再現するテスト計画を書く。

- 正常経路が完了する
- branch の条件経路と既定経路が正しく選ばれる
- parallel と join の待ち方が意図どおりである
- approval の承認、却下、期限切れが区別される
- loop が成功条件で止まり、上限到達時に無限実行しない
- 失敗時に意図したノード状態と利用者向けメッセージになる

最後に、設計書だけを初めて読む人が「何を入力し、どこで止まり、何が成功で、失敗時に何が起きるか」を説明できるか確認する。説明できない箇所は未決事項として残す。

## Mermaid の記法

テンプレートの図を変更するときは、次の規約を守る。

- node ID は英数字だけにする。実際の node ID と一致させる場合も、ハイフン以外の記号を避ける
- 日本語ラベルは必ず二重引用符で囲む
- flowchart のエッジラベルは `-->|"条件"|` 形式を使う
- sequence diagram の participant ID は英数字、表示名は二重引用符で囲む
- Mermaid の図にだけ存在する概念上のノードは、実装対象か説明専用かを注記する
- ループの戻り線には `loopBack: true` と対応する注記を付ける

## 出力形式

設計書を作る場合は `references/graph-design-template.md` を複製し、次の順序を保つ。

1. 文書情報と目的
2. 入力、出力、成功条件、前提
3. Mermaid の全体フローと実行シーケンス
4. ノード一覧と責務
5. エッジ、条件、既定経路、loopBack
6. データ契約と参照
7. 失敗、復旧、承認、安全性
8. 並列、ループ、予算、観測性
9. `graph.yaml` への写像
10. 検証、テスト、未決事項、レビュー項目

ユーザーが「テンプレートだけ」を求めた場合は、実在しない agent 名や業務固有のノードを埋めず、プレースホルダーのまま返す。ユーザーが具体的なグラフの設計を求めた場合は、テンプレートを埋めながら仮定と未決事項を分離する。

## 完了条件

- 業務の成功条件が、グラフの終端と後続テストで確認できる
- 各ノードに責務、入力、出力、完了条件、失敗時の扱いがある
- Mermaid、ノード表、エッジ表、YAML 草稿の対応が取れている
- 分岐の既定経路、並列の合流、ループの上限、承認の位置が明示されている
- 秘密情報を含まず、危険な操作の承認境界が明示されている
- 検証コマンド、テストシナリオ、未決事項が残っている
